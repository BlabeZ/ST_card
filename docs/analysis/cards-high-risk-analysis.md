## 标准字段使用情况

| 字段 | 非空卡数 | 非空中位字符数 | 最大字符数 | 观察 |
| --- | ---: | ---: | ---: | --- |
| `name` | 113 | 6 | 35 | 基本正常 |
| `description` | 75 | 2985 | 20736 | 承担大部分设定 |
| `personality` | 1 | 279 | 279 | 几乎废置 |
| `scenario` | 2 | 77 | 174 | 几乎废置 |
| `first_mes` | 113 | 206 | 317 | 被统一外部说明占用 |
| `mes_example` | 2 | 7 | 399 | 几乎没有角色语音校准 |
| `creator_notes` | 17 | 27 | 93 | 安装和依赖说明不足 |
| `system_prompt` | 0 | 0 | 0 | 行为规则被转移到世界书 |
| `post_history_instructions` | 0 | 0 | 0 | 未使用 |

### `description`

这个字段承担了身份、经历、关系、行为规则、语言特征和输出格式。部分卡把整个角色模板甚至状态规则都放在这里，导致单字段超过两万字符。

优点是导入后无需额外触发即可获得完整设定。缺点是每轮都要携带大量内容，人物事实、写作规则和状态协议也难以分别维护。

### `first_mes`

111 张卡使用完全相同的 206 字外部说明，另外两个数据库变体共享另一份 317 字说明。默认开场因此没有叙事功能。

51 张卡又没有备用开场。用户导入这些卡以后，第一条消息只能看到外部说明，无法直接进入故事。

### `alternate_greetings`

246 个备用开场共约 43 万字符，中位长度 1338，最大长度 10947。它们承担了以下职责。

1. 替代失效的默认开场。
2. 切换玩家身份、地点和故事时间点。
3. 选择当前出场角色或人物组合。
4. 初始化状态变量和路线标记。
5. 提供难度、视角或情绪方向。

53 个备用开场含状态或变量初始化结构。部分开场同时塞入数千字背景和规则，已经接近第二份世界书。好的开场应只确定当前局面、人物目标和玩家可行动空间。

### 其他字段

`personality`、`scenario` 和 `mes_example` 的缺失使角色表现依赖模型从长篇 `description` 或世界书中自行提炼。模型更换、上下文裁剪或条目未触发时，角色声音容易漂移。

`system_prompt` 和 `post_history_instructions` 全空，说明创作者习惯把叙事规范和强制规则放进常驻世界书。这种写法方便从编辑器开关模块，但不利于区分角色事实与全局行为要求。

## 内嵌世界书

### 条目分类

1454 条 entry 没有原生内容类型。按 `comment`、名称、关键词和正文结构分类后，可得到下列分布。

| 类型 | 数量 | 占比 | 常见内容 |
| --- | ---: | ---: | --- |
| 人物 | 692 | 47.6% | 身份、经历、性格、关系、语言和秘密 |
| 地点 | 86 | 5.9% | 房间、区域、机构和可发生事件 |
| 规则 | 476 | 32.7% | 叙事约束、输出格式、角色边界和世界规则 |
| 状态 | 98 | 6.7% | 时间、关系、任务、变量和面板格式 |
| 事件 | 102 | 7.0% | 开局、任务、随机事件、路线和结局条件 |

人物和规则占到八成，地点与事件条目相对少。主要依赖人物档案驱动的卡，如果没有额外的剧情机制，能够按需注入的行动场所和事件材料会比较有限。

### 规模和常驻成本

1454 条正文合计 2,219,089 字符，中位单条 836 字符，最大单条 30,446 字符。

| 状态 | 条数 | 正文字符量 |
| --- | ---: | ---: |
| 启用 | 1296 | 1,975,559 |
| 启用且常驻 | 785 | 1,341,768 |
| 启用且非常驻 | 511 | 633,791 |
| 禁用 | 158 | 243,530 |

单卡最大的启用常驻量达到 62,068 字符。常驻规则过多时，世界书失去按需检索的作用，并显著压缩聊天历史和当前场景的上下文空间。

### 插入位置

| 顶层 `position` | 数量 |
| --- | ---: |
| `before_char` | 634 |
| `after_char` | 810 |
| 空值 | 10 |

| `extensions.position` | 数量 | 常见含义 |
| --- | ---: | --- |
| 0 | 635 | 角色定义前 |
| 1 | 316 | 角色定义后 |
| 2 | 17 | Author's Note 顶部 |
| 3 | 12 | Author's Note 底部 |

顶层位置只表达兼容性较好的粗略位置。具体 SillyTavern 行为通常由 `extensions.position`、`depth` 和 `role` 决定。只读取顶层字段会误判大量状态和规则条目。

### 触发策略

- 主触发键共 2879 个，精确去重后 1732 个。
- 137 个键只有一个字符，容易在普通对话中误触发。
- secondary key 只有 31 个，分布在 8 条 entry。
- 1415 条设置 `selective: true`，其中 1407 条没有 secondary key。
- 1307 条设置 `use_regex: true`，但键仍然是普通文本形式。
- 28 本世界书存在跨 entry 的重复键。
- 270 条常驻 entry 仍保留触发键，增加维护噪声。

该目录大量依赖短关键词和重复关键词。人物姓名适合作为触发键，单字符称谓、常用关系词和“状态”“规则”一类宽泛键则可能一次激活多条。

`selective: true` 配空 secondary key 的兼容性判断来自静态字段分析，本次没有在 SillyTavern UI 中逐条复现。新卡应只在确实需要二级条件时开启 selective，并明确选择 ANY、ALL 或排除逻辑，再用目标客户端验证。

### 明确的数据问题

- 35 条正文为空，其中 10 条仍启用。
- 28 条启用、非 constant、没有主键和扩展触发器。
- 代表样本 D 有 16 条正文存在但无法自动触发的 entry。
- 代表样本 A 有 15 条启用 entry 的有效概率为 0。
- 代表样本 A 的 ID 90 至 93 是启用、空正文、无键条目。
- 一张卡把 `extensions` 写成 `extensionsL`，并有 10 条缺少 ID。
- 一张卡把深度写成字符串 `"1"`，其余多数为数字。

这些问题说明部分卡保留了编辑器占位符、历史条目或未完成迁移。条目数量不能直接代表实际可用内容。

## 外挂世界书和 TXT 生产资料

10 个 JSON 中有 2 个是角色卡副本，另外 8 个是外挂世界书。8 本外挂书物理上共有 146 条，去除完全重复文件后只有 5 种载荷、101 条不同 entry。

外挂世界书集中在四个子目录中，每个目录通常包含一份状态关系系统和一份强化规则。三份同名强化书完全相同，状态书则出现版本分叉。重复导入会叠加相同指令。

38 个 TXT 可分为 17 份人物设定、18 份开局、2 份生成说明和 1 份玩家设定。它们展示了一种可复用的生产流程。

1. 人物资料单独保存。
2. 每个人物配一份独立开局。
3. 通过生成说明统一格式。
4. 最后合并进角色卡和世界书。

这种“人物模块与开局模块分离”的工作方式值得保留。本文只保留该生产流程的结构结论。

## Regex 与 TavernHelper

### Regex

34 张卡实际包含 Regex，共 122 条，其中 101 条启用。

| 用途 | 观察 |
| --- | --- |
| 状态块识别 | 捕获 XML、代码块或类 JSON 状态 |
| 显示美化 | 73 条生成 HTML 或 CSS |
| 内容隐藏 | 41 条删除或隐藏内部块 |
| 提示裁剪 | `promptOnly` 控制模型是否继续看到内容 |
| 编辑重算 | 117 条启用 `runOnEdit` |

37 条替换文本含 `<script>`，其中 30 条启用。13 条含内联事件处理器，其中 12 条启用。Regex 由显示工具扩展成脚本容器后，安全边界、兼容性和调试成本都会明显恶化。

### TavernHelper

14 张卡使用现代 `TavernHelper_scripts`，另有 1 张使用旧式字段。现代脚本 18 个，旧式脚本 4 个。

- 20 份脚本文本包含外部 URL。
- 18 个现代脚本属于远程静态导入。
- 脚本合计约 35 万字符。
- 两个数据库变体各嵌入一份 174,376 字符的相同数据库脚本。
- 脚本可以访问网络、DOM、本地存储和聊天消息。

这类卡应按可执行扩展审计，不能按普通文本角色卡对待。远程脚本没有固定不可变版本和哈希时，上游内容变化可能在资源成功加载并执行后改变本地运行行为。

## 代表结构

### 代表样本 A

94 条世界书，是目录中条目数最多的卡。它展示了大型人物索引和多入口结构，也同时保留概率为 0、空正文和无键条目，是“资料很多但需要清理”的典型。

### 代表样本 B 的两个版本

两张卡都使用 61 条世界书和 6 个备用开场。57 条人物资料配合少量常驻规则，展示了同一结构替换主题内容的版本化方法。

### 代表样本 C

54 条世界书、6 个备用开场、6 个 Regex 和 TavernHelper。人物、世界、任务、变量和文风分层较完整，是角色卡、世界书和状态 UI 联动的代表。

### 代表样本 D

35 条世界书、约 13 万字符。资料量很大，脚本依赖较少，但有大量正文无触发入口，体现了“编辑器里存在，运行时不可达”的问题。

### 代表样本 E 与 DLC

基础版和 DLC 通过替换世界书模块扩展内容，角色卡正文保持较轻，适合作为模块化发行的结构参考。

### 代表样本 F 的两个版本

人物模块从 19 条扩展到 24 条，并配套 Regex 和 TavernHelper。两版都嵌入一份 174,376 字符的数据库脚本，在本目录中拥有最大的单脚本体量和最广的网络、DOM、存储及聊天消息访问面。

## 有效创作方法

### 人物

- 把身份、经历、动机、能力、边界和语言风格分开描述。
- 让性格能够从经历和目标中推导，减少形容词清单。
- 为人物设置知识盲区、现实限制和主动目标。
- 用示例对话校准句式、称呼、回避方式和冲突反应。

### 世界书

- 人物、地点、规则、状态和事件分成不同 entry。
- 人物使用姓名与稳定别名触发。
- 地点条目只记录当前有效事实和行动机会。
- 事件条目写触发条件、公开信息、后续影响和结束条件。
- 常驻条目只保存不可变规则和简短状态协议。

### 开场

- 每个开场代表一个清晰且互斥的初始状态。
- 第一段立即给出人物目标、当前变化和玩家可采取的行动。
- 变量初始化与叙事正文分开，避免开场变成整份设定。
- 默认开场必须可直接游玩，备用开场用于真正不同的路线。

### 状态

- 只记录时间、地点、任务、资源、公开关系阶段等可验证信息。
- 状态脚本或表格作为唯一真值，Regex 只负责展示。
- 重生成、切换聊天和上下文裁剪后应能恢复状态。
- 每次更新只改变实际发生变化的字段。

## 主要失败模式

1. `description` 无限增长，标准人格、场景和示例字段长期空置。
2. 将大部分世界书设为 constant，造成固定上下文成本。
3. 依赖单字符、重复和宽泛关键词，导致批量误触发。
4. 状态栏由模型自由填写，没有权威变量源。
5. Regex 同时负责格式化、隐藏、提示改写和脚本执行。
6. 通过复制目录保存版本，卡片和外挂世界书逐渐分叉。
7. 默认开场被推广信息占用，导入后的第一体验失效。
8. 大量强制措辞压过人物目标，角色只能机械复现设定。

## 对自制角色包的参考价值

适合直接借鉴的部分包括多开局组织、人物与地点分条、事件条目、状态恢复、模块化 DLC 和角色资料与开局资料分离。

需要重做以后再采用的部分包括大型状态 UI、变量数据库和群像主持结构。它们必须有本地开发源、版本固定、测试和降级路径。

不应直接采用的技术实现包括通过 Regex 隐藏内部提示、未审计远程脚本，以及用复制目录代替版本管理。

与八个自制角色包的具体差距和改进建议见 [`role-package-comparison.md`](role-package-comparison.md)。

## 统计限制

- Entry 分类来自字段和文本标记规则，不是 SillyTavern 原生类型。
- 字符数用于比较相对规模，不能直接等同于具体模型的 token 数。
- 静态分析没有模拟全局 World Info 预算、递归、扫描深度和 Inclusion Group 的完整组合。
- Regex 和 TavernHelper 只检查保存内容，没有在浏览器或 SillyTavern 中执行。
- 关于误触发、兼容性和脚本权限的结论属于待目标版本复现的风险判断。
